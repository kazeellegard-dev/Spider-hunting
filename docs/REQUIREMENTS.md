## 0. 確定事項（v0.2で決定）

| 項目 | 決定内容 |
|---|---|
| 収益モデル | **広告＋課金ハイブリッド**。基本無料プレイ＋リワード広告（スタミナ回復・巣修復即時化・ボーナスステージ再挑戦等）＋アイテム課金（強化素材・広告除去等）を併用する。 |
| 表現の過激度 | **ライト表現**。虫は糸にぐるぐる巻きにされて少し間を置いてから「ポン」と消える演出とし、血・体液・断末魔等のグロテスク表現は一切含めない。対象年齢は12+相当を想定。 |
| 開発エンジン | **SpriteKit（Swiftネイティブ）**。iOS専用で展開し、開発者はSwift/iOS開発経験ありのため学習コストが最小。StoreKit 2（課金）・GameKit（実績/ランキング）・広告SDKとのネイティブ連携がしやすく、ビルド/審査まわりの余計な依存も避けられる。 |
| ゲームループ構造 | **ハイブリッド（エンドレス＋マイルストーン進行）**。1プレイはスタミナが尽きる／巣が破壊されるまで続くエンドレスの捕獲プレイ。並行して、累計スコアやレベルの節目（マイルストーン）でエリア（背景・出現する虫のセット）が切り替わり、ステージ制のような「進んでいる感」を演出する。個別のステージクリア／失敗判定は設けない。 |

以降の各章は、この4点を前提として記述する。

### 0.1 開発エンジン選定理由

| 比較軸 | SpriteKit（採用） | Unity | Godot |
|---|---|---|---|
| 対応スキル | Swift経験ありなので学習コストほぼゼロ | C#/Unity未経験なら学習コスト大 | GDScript/C#とも未経験なら学習コスト大 |
| クロスプラットフォーム | iOS専用（今回はAndroid展開なしのため問題なし） | 強み（今回は活かせない） | 強み（今回は活かせない） |
| StoreKit/GameKit/広告SDK連携 | ネイティブAPIなので直結、余計なブリッジ層が不要 | プラグイン経由（Unity IAP、Mediation SDK等）でひと手間 | プラグインの成熟度が低くiOS IAP/広告まわりの事例が少ない |
| ビルド・審査 | Xcode標準ビルドのみで完結、アプリサイズも小さい | IL2CPPビルドでサイズ増・ビルド時間増の傾向 | 情報少なく審査事例の知見が薄い |
| ライセンス/コスト | 無料（Appleネイティブ） | 収益しきい値超過でUnityライセンス費が発生し得る | 無料（オープンソース） |
| 2D物理・糸表現 | 標準の`SKPhysicsJoint`では糸の柔軟な垂れ下がりは非対応。Verlet Integration等を自前実装する前提（T-02で詳細調査） | 高機能な物理エンジン・アセットが豊富だが今回はオーバースペック | 2D物理は一定水準だが糸表現の実装事例はSpriteKit同様に自前実装が必要 |

**結論**: 「iOS専用」「Swift経験あり」という2条件がUnity/Godotの強み（クロスプラットフォーム、豊富なアセットエコシステム）を打ち消すため、開発速度・保守性・審査の通しやすさで勝るSpriteKitを採用する。糸の物理表現はSpriteKit標準機能でカバーしきれないため、Verlet Integrationベースの自前実装を行う（T-02）。

### 0.2 ゲームループ構造の選定理由

| 比較軸 | ステージ制 | エンドレス制 | ハイブリッド（採用） |
|---|---|---|---|
| 既決の収益モデルとの相性 | スタミナ制と役割が重複し設計が複雑化しやすい（ライフ制との二重管理になりがち） | リワード広告での「スタミナ即時回復」がそのままコアループの継続動機になり、相性が良い | エンドレス部分はスタミナ制と直結。マイルストーンは広告・課金の追加動機（先出しでエリア解放等）にも使える |
| 進行感・目標の明確さ | 明確（クリア/未クリアが分かりやすい） | 弱い（スコアのみだと目標が単調） | エリア切り替え・新しい虫の解放で「進んでいる感」を補える |
| 実装コスト | ステージデータ・クリア条件・進行管理が必要で工数大 | 最小（スコアと難易度カーブのみ） | エンドレス基盤＋マイルストーン判定の追加のみで、ステージ制ほどの工数増にはならない |
| セッション長への影響 | ステージ設計次第で1プレイが伸びやすく、隙間時間向けのコンセプトとズレる | 1プレイ1〜3分の想定に合う | エンドレスと同様、1プレイの長さはスタミナで制御できる |

**結論**: 「広告でスタミナを回復して繰り返し遊ぶ」という既決の収益モデルに最も自然に接続できるのはエンドレス基盤であるため、これを採用する。ただし進行感を出すため、レベル・累計スコアの節目でエリア（背景・出現する虫のセット）が切り替わる「マイルストーン進行」を組み合わせる。個別のステージごとのクリア／失敗判定は設けない。

## 1. アプリ概要

| 項目 | 内容 |
|---|---|
| タイトル（仮） | クモの巣ハンティング（Spider Hunting） |
| ジャンル | カジュアルアクション／育成 |
| プラットフォーム | iOS（iPhone優先、iPad対応は要検討） |
| 操作方法 | タップ／ドラッグ（片手プレイ想定） |
| プレイセッション長 | 1プレイ 1〜3分程度（隙間時間向け） |
| コンセプト | クモを操作し、飛来する虫を巣にかけて捕食。成長させて巣を強化し、より大きな獲物やボーナスステージに挑戦する |

### 1.1 一言コンセプト
「巣を張り、待ち、仕留める」というクモらしい駆け引きを、タップ操作で気持ちよく再現するカジュアルゲーム。

## 2. ターゲットユーザー・想定ペルソナ

- カジュアルゲームを隙間時間に遊ぶ層（通勤・通学、待ち時間）
- 育成・コレクション要素が好きな層
- 虫や生き物モチーフに抵抗がない年齢層（要検討: 低年齢層向けにデフォルメ度を上げるか、ホラー/グロ表現を避けるか）

### 2.1 対象年齢・レーティング
- 表現方針は「ライト表現」（0章参照）に確定。虫が糸に巻かれてポンと消える程度で、血・グロ表現なし。App Store年齢レーティングは12+程度を想定（最終区分はB-01/B-02の調査結果で確定する）。

## 3. 機能要件

### 3.1 コアゲームプレイ：虫を捕まえる
- **F-01**: 画面内にハエ・蚊・蝶などの虫がランダムな軌道・速度で出現し、画面を横切って飛ぶ。
- **F-02**: クモの巣（糸）に虫が接触すると捕獲判定が発生する。
- **F-03**: 虫ごとに「重さ／耐糸力」パラメータを持ち、クモの糸の強度が虫の重さを下回ると糸が切れる（捕獲失敗、巣の一部破損）。
- **F-03a**: 捕獲成功時の演出は「ライト表現」に統一する。虫は糸にぐるぐる巻きにされ、短い間（1秒程度）を置いてから光の粒になってポンと消える。血・体液・断末魔などグロテスクな表現は一切含めない。
- **F-04**: 捕獲成功時にスコア・経験値・ゲーム内通貨を獲得する。
- **F-05**: ゲームループは「ハイブリッド（エンドレス＋マイルストーン進行）」に確定（0.2章）。1プレイはスタミナ（糸の総量、F-15）が尽きる、または巣が完全に破壊されると終了する。個別ステージのクリア／失敗判定は設けない。
- **F-05a**: 累計スコアまたはプレイヤーレベルが一定の節目（マイルストーン）に達すると、エリア（背景・出現する虫のセット）が切り替わる。エリア一覧・切り替え条件はゲームバランス設計（6章）で定義する。
- **F-06**: 虫の種類ごとに得点・出現頻度・出現エリア（F-05aのマイルストーンで解放）が異なる。

### 3.2 レベル・成長システム
- **F-07**: プレイヤー（クモ）にレベルの概念があり、経験値蓄積でレベルアップする。
- **F-08**: レベルアップにより「糸の強度」「巣の最大サイズ」「糸の伸ばせる本数」などのパラメータが向上する。
- **F-09**: 糸の強度が上がると、より重い（大きい）虫を捕獲できるようになり、出現する虫のバリエーションが解放される。
- **F-10**: レベル/強化要素をツリー状（スキル振り）にするか、単純な自動成長にするかは要検討。
- **F-11**: 成長は基本ゲーム内通貨（プレイで獲得）で進行できる設計とし、課金は「時短（強化素材の直接購入）」の位置づけとする。強化そのものを課金限定にはしない（無課金プレイヤーの離脱防止）。

### 3.3 巣の作成（タップでクモを移動・巣を張る）
- **F-12**: プレイヤーが画面上の任意の位置をタップすると、クモがその位置へ移動する。
- **F-13**: クモの移動軌跡、または指定した複数のアンカーポイント間に「糸」が自動的に張られ、巣の形状を構築する。
- **F-14**: 巣の形状（面積・網の密度・アンカー数）が捕獲率・耐久力に影響する設計とする。
- **F-15**: 糸の総量に上限があり（スタミナ／リソース制）、無限に巣を拡張できないようにする。
- **F-16**: 巣が虫や外的要因（風、天敵など）で破損した場合の修復手段（自動回復／タップで補修）を定義する。
- **F-17**: 巣作成のUI/UX：タップ位置の視覚的フィードバック（プレビュー線、糸を張れない範囲の表示など）。

### 3.4 ボーナスステージ
- **F-18**: 一定条件（コンボ数、特定アイテム取得、時間経過など）でボーナスステージへ移行する。
- **F-19**: ボーナスステージでは飴・お菓子などのアイテムが降ってくる／飛んでくる演出とし、通常ステージとは異なる収集目的とする。
- **F-20**: ボーナスステージで得たアイテムの用途（ゲーム内通貨、育成素材、ガチャ的要素など）を定義する。
- **F-21**: ボーナスステージの発生頻度・持続時間・難易度カーブを定義する。

### 3.5 その他機能（洗い出しレベル・優先度は要検討）
- **F-22**: タイトル／ホーム画面。ステージ選択画面は設けず、ホームから直接エンドレスプレイに入る導線とする。到達済みエリア・マイルストーン進捗はホーム画面上に表示する。
- **F-23**: 設定画面（サウンドON/OFF、通知設定、言語設定等）
- **F-24**: 実績・デイリーミッション・ログインボーナスなどのリテンション施策
- **F-25**: ランキング（Game Center連携）の要否
- **F-26**: チュートリアル（初回起動時の操作説明）
- **F-27**: 収益化は「広告＋課金ハイブリッド」（0章で確定）。内訳案:
  - リワード広告: スタミナ（糸の総量）即時回復、巣の即時修復、ボーナスステージ再挑戦、獲得通貨2倍
  - バナー広告: ホーム画面下部など非プレイ画面中心に表示し、プレイ体験は阻害しない
  - アイテム課金: 強化素材パック、限定コスチューム（クモの見た目）、広告完全除去パス
  - ガチャ的課金要素を入れるかは要検討（射幸性への配慮、ガイドライン確認が必要）
- **F-28**: プッシュ通知（巣の修復完了、スタミナ回復、イベント告知など）

## 4. 非機能要件

| 分類 | 要件（案） |
|---|---|
| 対応OS | iOS 16以上を想定（要最終決定） |
| 対応端末 | iPhone SE以降の主要機種、iPadは別レイアウト対応が必要か要検討 |
| フレームレート | 60fps（軌道計算・物理演算のパフォーマンス確保） |
| オフライン対応 | 基本オフラインでプレイ可能、ランキング/課金/広告時のみ通信 |
| データ保存 | ローカル保存必須、iCloud経由の機種間引き継ぎは要検討 |
| ローカライズ | 日本語必須、英語対応の要否は要検討（グローバル展開するか） |
| アクセシビリティ | 色覚多様性対応（虫の視認性）、VoiceOver対応の要否 |
| セキュリティ/プライバシー | 個人情報を扱わない前提だが、広告SDK・分析SDK導入時はATT（App Tracking Transparency）対応が必要 |

## 5. 画面構成（案）

1. スプラッシュ／タイトル画面
2. ホーム画面（プレイ開始、到達エリア・マイルストーン進捗表示、育成・強化、ショップ、設定への導線。ステージ選択画面は設けない）

5. 育成／強化画面（レベル・パラメータ確認、アイテム使用）
6. ショップ画面（課金・ガチャ等がある場合）
7. ボーナスステージ画面
8. 設定画面

## 8. 調査項目一覧

### 8.1 技術調査
- ~~**T-01** iOSゲーム開発エンジンの比較検討~~ → SpriteKitに確定（0.1章）。以降の技術調査はSpriteKit前提で実施する。
- **T-02** SpriteKit上での糸（ライン）のVerlet Integration実装方法の調査（`SKShapeNode`での描画更新頻度とパフォーマンス、`SKPhysicsJoint`との併用可否）
- **T-03** タップ位置へのオブジェクト移動＋経路上への線描画（巣作成）のアルゴリズム調査（SpriteKitの`SKAction`によるmove、`CGPath`を用いた糸描画の既存実装事例）
- **T-04** 多数の虫オブジェクトを同時に動かす際のパフォーマンス最適化手法（Object Pooling、描画バッチ等）
- **T-05** セーブデータの実装方式（UserDefaults / Core Data / SwiftData / iCloud同期）の比較
- **T-06** Game Center連携（実績・ランキング）実装の要否と工数
- **T-07** 広告SDK（Google AdMob等）導入時のATT対応・プライバシーマニフェスト対応調査（2024年以降のApp Store要件）
- **T-08** In-App Purchase実装（消耗型／非消耗型アイテム、StoreKit 2の利用）
- **T-09** 通知（ローカル通知／プッシュ通知）実装方式

### 8.2 ゲームデザイン・UX調査
- **D-01** 競合カジュアルゲーム調査（虫取り系、育成系、タップ操作系の類似アプリのゲームループ・マネタイズ分析）
  - 例: 虫取り・釣り・キャッチ系カジュアルゲームのApp Store上位タイトルのレビュー分析
- **D-02** 片手操作を前提としたUIレイアウトのベストプラクティス調査
- **D-03** 「クモ」というモチーフに対するユーザー受容性調査（好悪感情、忌避感への配慮方法：デフォルメデザインの参考事例）
- **D-04** ボーナスステージ的なミニゲーム構造の類似事例調査（コンボ演出、報酬設計）
- **D-05** リテンション施策（デイリーミッション、ログインボーナス等）の効果に関する事例調査

### 8.3 ビジネス・法務・審査関連調査
- **B-01** 「ライト表現」（F-03a）がApp Store年齢レーティング質問票上、実際に12+相当に収まるか、9+まで下げられるかの確認（App Store Connectのレーティング質問票の該当項目を精査）
- **B-02** 広告＋課金ハイブリッド運用時のガイドライン制約確認（リワード広告の実装規約、IAP価格帯の設定、未成年課金への配慮・ペアレンタルコントロール表示義務の有無）
- **B-03** 広告SDK・メディエーション（AdMob等）の単価相場、リワード広告ユニットの一般的なeCPM、カジュアルゲームのIAP価格帯・ARPU相場調査
- **B-04** ガチャ的課金要素を含める場合の景品表示法・確率表示義務（国内配信時）の確認、含めない場合の代替インセンティブ設計
- **B-05** 昆虫・生物モチーフの著作権／商標的な問題有無の確認（実在種を模したデザインを使う場合の注意点）
- **B-06** BGM・効果音の権利関係（自作／ロイヤリティフリー素材／外部発注）の方針決定

### 8.4 アート・サウンド調査
- **A-01** アートスタイルの方向性検討（デフォルメ・ゆるキャラ調 vs リアル調）とターゲット層との整合性確認
- **A-02** 虫・クモのキャラクターデザイン参考事例収集
- **A-03** 効果音・BGMの参考事例収集（捕獲音、巣作成音、レベルアップ演出音）
